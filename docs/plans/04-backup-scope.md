# 백업 범위 확정과 가져오기 부분 실패 정책

S02 "전체 데이터 내보내기"(`app/settings.tsx:67`)와 S21 여행 내보내기의 실제 범위를 화면 문구와 일치시키고,
여러 여행 가져오기 중 하나가 실패할 때의 동작을 문서·코드·안내가 같은 말을 하도록 고친다.
`01-p0-flow-and-data-bugs.md` 이후, `02`와 순서 무관하게 실행할 수 있다.

## 왜 필요한가

- `db/backup.ts:14-44`는 여행별로 `trips`·`trip_days`·`day_items`·`saved_places`·참조된 `places`·`expenses`·`checklist_items`만
  내보낸다. `chat_messages`는 의도적으로 제외(`:42` 주석)하고 `app_settings`는 import 목록(`:12`)에도 없다.
  화면은 "전체 데이터"라고 말한다.
- `db/backup.ts:79` 독스트링은 "하나가 실패해도 나머지는 남는다"라 하지만 `:80-101` 루프에 `try/catch`가 없어
  예외가 루프를 끊는다. 앞서 커밋된 여행은 남고 뒤 여행은 시도되지 않으며, 호출자(`app/settings.tsx:52-55`)는
  "가져오지 못했어요" 한 줄만 보여준다. 몇 개가 들어갔는지 사용자는 모른다.
- 같은 백업을 두 번 가져오면 `lib/backup.ts:76-84`가 모든 id를 재발급해 여행이 둘 생긴다. 이것은 설계 결정(§8-12
  "덮어쓰지 않는다")이며 버그가 아니지만, 화면 문구(`app/settings.tsx:96-98`)가 이미 그렇게 설명하는지 확인 대상이다.

## 범위 밖

- 파일 선택기(`expo-document-picker`)·공유 시트 확장. 붙여넣기 방식을 유지한다(§8-12).
- 클라우드 동기화·자동 백업. §1.3-2의 "유일한 백업 수단은 JSON"을 바꾸지 않는다.
- AI 채팅 기록 자체는 `09-ai-chat.md`가 만든다.

## 실행 조건

- 플랜 01 완료 후.
- 백업 버전을 올리면 **버전 1 파일 가져오기가 계속 되어야 한다**. `lib/backup.ts:35-37`이 "더 새로운 버전"만 거부하므로
  버전 2 파서는 버전 1 페이로드를 기본값으로 채워 읽어야 한다. 이것이 안 되면 실행하지 않는다.

## 결정

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| `chat_messages` | **포함한다.** 백업 버전 2 | 채팅은 09 플랜에서 여행별 로컬 DB에 저장되는 사용자 데이터가 된다. "기기 이전 시 대화가 사라진다"를 사용자가 예측할 수 없다 |
| `app_settings` | **포함하지 않는다** | `onboarded`·`tip_*`·날짜 형식은 기기 상태다. 새 기기에서 온보딩과 코치마크를 다시 보는 것이 옳다 |
| 화면 문구 | `전체 여행 데이터 내보내기` + 보조 문구에 "앱 설정은 포함되지 않아요" | 실제 범위를 이름으로 말한다 |
| 부분 실패 | **여행별 독립 처리.** 실패한 여행만 건너뛰고 결과에 "N개 가져옴, M개 실패(제목)"를 보여준다 | 독스트링(`:79`)이 약속한 동작을 실제로 만든다. 전체 롤백은 여행이 많을수록 사용자 손실이 크다 |

## 절차

1. `lib/backup.ts:5` `BACKUP_VERSION`을 2로 올리고 `TripPayload`(`:20` 인접 타입)에 `chatMessages` 배열(선택)을 추가한다.
   `parseBackup`(`:25-46`)은 버전 1 페이로드에서 이 필드를 빈 배열로 취급한다. 근거: 실행 조건.
2. `db/backup.ts:14-44` 여행별 export에 `chat_messages`(`db/schema.ts:99-105`) 조회를 추가하고 `:42` 주석을 지운다.
3. `lib/backup.ts:76-131` `planImport`에서 재매핑 시 `chat_messages.trip_id`도 새 id로 바꾼다. `lib/check.ts:238` 백업 절에
   "버전 1 파일 → 채팅 없음으로 통과", "버전 2 재매핑 시 채팅 trip_id 갱신" 두 케이스를 추가한다.
4. `db/backup.ts:80-101` 루프 본문을 `try/catch`로 감싸 여행별 성공·실패를 수집하고, 반환값을 `{imported, failed:[{title, reason}]}`
   형태로 바꾼다. 트랜잭션은 이미 여행별(`:87-95`)이므로 실패한 여행의 자식 행은 남지 않는다.
5. `app/settings.tsx:52-55`의 결과 알림을 반환값 기반으로 바꾼다. 전부 성공·일부 실패·전부 실패 세 문구를 둔다.
6. `app/settings.tsx:67` 문구를 `전체 여행 데이터 내보내기`로, `:78-80` 보조 문구에 "앱 설정은 포함되지 않아요"를 추가한다.
   S21의 내보내기 버튼 문구(`app/trip/[id]/settings.tsx` 내 export 행)도 "이 여행 내보내기"로 범위를 명시한다.
7. `docs/design.md` §8-10 "`chat_messages`는 내보내지 않는다"와 §8-12 봉투 설명을 버전 2 기준으로 고친다.

iOS 시뮬레이터:

1. 채팅 메시지가 있는 여행(09 플랜 전이면 `sqlite3`로 `chat_messages` 행을 직접 넣는다)을 전체 내보내기 → JSON에
   `version: 2`와 `chatMessages`가 있다. `app_settings` 키는 없다.
2. 같은 JSON을 두 번 가져오기 → 여행 2개, 각각 자기 `chat_messages`를 가진다. 기존 여행은 그대로다.
3. 버전 1 형식 JSON(현재 HEAD로 내보낸 파일을 미리 저장해 둔다)을 가져오기 → 성공, 채팅 0건.
4. 여행 3개짜리 JSON에서 두 번째 여행의 `trips.start_date`를 손상시켜 가져오기 → 1번·3번 여행이 들어가고 알림이
   "2개 가져옴, 1개 실패"를 보여준다. `sqlite3`로 2번 여행의 자식 행이 없음을 확인한다.

## 되돌리는 법

`BACKUP_VERSION`을 2로 올린 뒤 되돌리면 이미 버전 2로 내보낸 파일이 "더 새로운 버전"으로 거부된다. 되돌릴 때는
상수만 내리지 말고 파서의 버전 상한 검사(`lib/backup.ts:35-37`)를 함께 완화한다. 상향 신호: 가져오기 실패 알림에
`version` 관련 메시지가 반복되면 파서 호환이 깨진 것이다.

## 기각한 대안

- **`app_settings` 포함** — 코치마크 플래그와 온보딩 완료를 옮기면 새 기기 사용자가 안내를 못 본다. 날짜 형식 하나 때문에 넣을 가치가 없다.
  기기 상태가 아닌 설정이 3개 이상 생기면 재론.
- **가져오기를 전체 하나의 트랜잭션으로** — expo-sqlite 동기 트랜잭션에 여행 수십 개를 넣으면 UI가 멈추고, 하나의 손상이 전체를 막는다.
- **재가져오기 시 같은 id 여행을 갱신(merge)** — 어느 쪽이 최신인지 판단할 근거(수정 시각)가 스키마에 없다. `updated_at`이 생기면 재론.

## 실패 모드

버전 2 내보내기만 확인하고 **버전 1 파일 가져오기**를 검증하지 않는 것이 이 플랜의 실패 모드다. 기존 사용자의 백업이 그 형식이다.
